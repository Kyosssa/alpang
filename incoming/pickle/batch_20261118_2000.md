## 32차 방법(다음 회차에 그대로 쓸 것)

1. **신규 프리스크린 — `oar1~3.jpg`**: `i.ytimg.com/vi/<ID>/oar1.jpg`·`oar2`·`oar3`는 **원본 비율·원본 해상도**의 서로 다른 3프레임을 준다(예: 1080x1920 vs 720x1280). 이미지 호스트는 봇 차단이 없어 curl로 **무료·무제한**으로 해상도·정지 여부(3프레임 차분)·텍스트(RapidOCR)를 사전 판정할 수 있다. 이번 회차 강아지 136편 → 76편(해상도) → 22편(무자막)으로 압축해 브라우저 호출을 1/6로 줄였다.
2. **curl·yt-dlp 직접 접근은 여전히 불가**: 구글 어비스 302 + "Sign in to confirm you're not a bot". Invidious 8개 인스턴스 전부 사망(403/500/000) → 메타데이터 API 우회도 불가.
3. **모션 측정**: `/shorts/<ID>` 페이지에서 `videoWidth>0`인 활성 `<video>`를 고르고(로딩 전이면 0x0이 잡혀 n=0이 된다 → 최대 12초 대기 루프 필수), 0.05초 시크 → 1.3초 워밍업 → 0초 재측정 → 10.4초간 0.099초 버킷 10fps 160x90 gray 차분.
4. **8컷 육안**: 페이지에 1080x1920 캔버스를 `position:fixed`로 붙이고 2x2(셀 540x960 = 원본 50%) 그리드를 그려 스크린샷 2장으로 확인. 스파이크가 뜨면 ±0.5초 4컷을 추가로 떠 **컷/카메라 이동을 구분**한다(이번 회차 Dj1x·uM8·bahAzD 3편이 이 방식으로 실컷 아님을 확인).
5. **해상도 판정은 playerResponse**: 숏츠 페이지는 hd1080 강제가 먹지 않아 240x426~720x1280으로 디코드된다. 원본 해상도는 `ytInitialPlayerResponse.streamingData.adaptiveFormats`의 `1080x1920` 포함 여부로만 판정.
